## OpenTelemetry Collector — Notes

### 1. Check the available chart versions

```powershell
helm search repo open-telemetry/opentelemetry-collector
```

We selected chart version:

```text
0.173.1
```

---

### 2. Inspect the chart's default values

```powershell
helm show values open-telemetry/opentelemetry-collector --version 0.173.1
```

This helps us understand what the chart provides before creating our own `values.yaml`.

---

### 3. Check the Collector deployment mode

```powershell
helm show values open-telemetry/opentelemetry-collector --version 0.173.1 |
    Select-String "mode:" -Context 0,8
```

We found:

```yaml
mode: ""
```

The chart supports different deployment modes.

For our project we use:

```yaml
mode: deployment
```

**Why?**

We only need **one Collector instance** for this local Kind cluster.

We don't need a Collector running on every Kubernetes node, so `daemonset` would be unnecessary.

---

### 4. Check the Collector configuration

```powershell
helm show values open-telemetry/opentelemetry-collector --version 0.173.1 |
    Select-String "config:" -Context 0,25
```

This showed the main Collector configuration sections:

```yaml
config:
  receivers:
  processors:
  exporters:
  extensions:
  service:
```

These are important because they define the Collector pipeline.

Conceptually:

```text
Receiver → Processor → Exporter
```

For our project:

```text
FastAPI
   │
   │ OTLP
   ▼
Receiver
   │
   ▼
Processor
   │
   ▼
Exporter
   │
   ▼
Jaeger
```

---

### 5. Receiver

A **receiver** defines how the Collector receives telemetry.

For our application, we will use **OTLP**.

The FastAPI application will eventually send traces using:

```text
OTLP → OpenTelemetry Collector
```

We are not configuring the final Jaeger exporter yet because we're deliberately learning the Collector first.

---

### 6. Processor

The chart already provides processors such as:

```yaml
processors:
  batch: {}
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 25
```

**Why?**

`batch` groups telemetry before sending it onward.

`memory_limiter` helps prevent the Collector from consuming excessive memory.

For our local environment, these are useful defaults.

---

### 7. Exporter

The default chart contains:

```yaml
exporters:
  debug: {}
```

The `debug` exporter is useful while learning because it allows us to verify that the Collector is actually receiving telemetry.

Later, when Jaeger is installed, we'll change/add the exporter:

```text
Collector → Jaeger
```

So initially we can focus on:

```text
Application → Collector
```

before introducing another component.

---

### 8. Health check

The chart requires the `health_check` extension:

```yaml
extensions:
  health_check:
    endpoint: ${env:MY_POD_IP}:13133
```

**Why?**

It provides a health endpoint that Kubernetes can use to determine whether the Collector is healthy.

---

### 9. Check the Collector Service

```powershell
helm show values open-telemetry/opentelemetry-collector --version 0.173.1 |
    Select-String "service:" -Context 0,15
```

We found:

```yaml
service:
  type: ClusterIP
```

**Why `ClusterIP`?**

The Collector only needs to communicate **inside the Kubernetes cluster**.

Our flow is:

```text
FastAPI Pod
    ↓
Collector Service
```

We don't need to expose the Collector directly to the Windows host.

---

## Our initial `values.yaml`

So, for the **first Collector installation**, we keep it intentionally simple:

```yaml
mode: deployment

config:
  receivers:
    otlp:
      protocols:
        grpc:
        http:

  processors:
    batch: {}

  exporters:
    debug: {}

  extensions:
    health_check:
      endpoint: ${env:MY_POD_IP}:13133

  service:
    extensions:
      - health_check

    pipelines:
      traces:
        receivers:
          - otlp
        processors:
          - batch
        exporters:
          - debug

service:
  type: ClusterIP
```

The important learning point is that we're **not trying to build the complete observability stack yet**.

First we'll prove:

```text
OTLP telemetry
      ↓
OpenTelemetry Collector
      ↓
debug exporter
```

Then we'll install **Jaeger** and change the pipeline to:

```text
OTLP
 ↓
Collector
 ↓
Jaeger
```

OTLP Receiver

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
OTLP supports both gRPC and HTTP.
4317 → OTLP/gRPC
4318 → OTLP/HTTP
Explicit endpoints are used so the Collector listens on all pod interfaces.
An empty grpc: / http: configuration was not accepted by this Collector version.

Then we'll add the FastAPI auto-instrumentation and finally verify an actual trace end-to-end.

That gives us a clean learning progression rather than installing everything at once.
